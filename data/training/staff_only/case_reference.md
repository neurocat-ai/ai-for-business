# S1 case reference: внутренняя рамка для авторов и ревьюеров

Документ не задает единственный правильный ответ. Он описывает диапазон профессионально допустимых результатов S1.

## 1. Ожидаемая область аудита

Обработка входящих лидов и предпродажная коммуникация от первого обращения до следующего коммерческого шага.

Студент не должен начинать аудит с заранее выбранного "бота продаж" или заранее выбранной заявки на демо.

## 2. Процессы, которые студент может обнаружить

1. Разбор входящего лида.
2. Уточнение потребности.
3. Ответы по продукту.
4. Определение следующего шага.
5. Регистрация демо.
6. Передача сложных случаев.
7. Контроль качества коммуникации.

Формальная BPMN-модель не требуется.

## 3. Основные проблемные участки

- длинные и плохо структурированные обращения;
- потеря важных данных;
- повторяющийся поиск продуктовой информации;
- риск ошибочного обещания функций или условий;
- неоднородное решение о следующем шаге;
- ручной перенос данных;
- назначение слабо квалифицированных демо;
- необходимость ранней эскалации enterprise-запросов.

## 4. Допустимые кандидаты

### Кандидат A. Структурировать и резюмировать входящий лид
Потенциальный класс: Prompt-tool.
Сильные стороны: высокая реализуемость, доступные текстовые данные.
Ограничение: сам по себе не решает вопросы актуальных продуктовых знаний.

### Кандидат B. Проверять качество ответа менеджера
Потенциальный класс: Prompt-tool.
Сильные стороны: понятный текстовый вход.
Ограничение: нужно формализовать критерии качества.

### Кандидат C. Готовить ответы по продуктовой базе
Потенциальный класс: RAG.
Сильные стороны: много повторяющихся вопросов по функциям, тарифам, интеграциям и безопасности.
Ограничение: нужно корректно обрабатывать отсутствие ответа в базе.

### Кандидат D. Создавать заявку на демо по уже квалифицированному лиду
Потенциальный класс: Agent.
Сильные стороны: понятное безопасное внешнее действие.
Ограничение: нужны достаточные данные и решение о допустимости действия.

### Кандидат E. Обрабатывать лид от первого обращения до следующего коммерческого шага
Потенциальный класс: RAG + Agent.
Сильные стороны: сочетает понимание запроса, продуктовые знания и внешнее действие.
Ограничение: нужны правила квалификации, human confirmation и надежная эскалация.

### Кандидат F. Самостоятельно определять индивидуальную скидку
Потенциальный эффект: высокий.
Статус: слабый кандидат для текущего прототипа.
Причины: полномочия ограничены, данные об индивидуальных условиях неполны, ошибка напрямую влияет на коммерческие обязательства.

## 5. Что считать хорошим выбором

Студент может обоснованно выбрать A, B, C, D или E.

Выбор считается сильным, если студент:
- связывает задачу с бизнес-целью;
- сравнивает альтернативы;
- учитывает ценность, реализуемость, риски и готовность данных;
- формулирует проверяемую гипотезу и критерий успеха;
- не усложняет задачу только ради использования более сложного класса.

## 6. Логика последующих спринтов

Если основной кандидат:
- закрывается Prompt-tool, это корректный бизнес-результат;
- требует знаний, он естественно продолжается в S3;
- не требует знаний, RAG-эксперимент можно сделать на кандидате C;
- требует действия, он продолжается в S4;
- не требует действия, Agent-эксперимент можно сделать на кандидате D.

В S5 выбирается один target scenario. Нельзя механически склеивать RAG одного кандидата и Agent другого.

## 7. Данные и готовность

Ожидаемый вывод:
- история лидов доступна;
- продуктовая база доступна;
- данные по лидам и заявкам на демо доступны;
- безопасное создание заявки технически реализуемо;
- индивидуальные скидки и нестандартные обязательства не готовы к автономному решению.

## 8. Основные риски

- выдуманная функция;
- неверный тариф;
- обещание неподдерживаемой интеграции;
- выдуманное security-обязательство;
- преждевременное демо;
- потеря контакта или use case;
- ошибочный tool call;
- дубль заявки;
- отсутствие эскалации enterprise-кейса.

## 9. Допустимая концептуальная архитектура для сложного кандидата

входящий лид -> LLM-анализ -> продуктовая база знаний -> решение о следующем шаге -> подтверждение человека -> business tool -> внешнее состояние -> итог менеджеру.

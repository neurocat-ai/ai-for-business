# Tool contract: create_return_request

## Назначение
`create_return_request` представляет внешнее бизнес-действие: зарегистрировать заявку на разбор возврата или проблемного заказа.

Техническая реализация может использовать Google Sheet + подготовленный endpoint / Apps Script. Для студента это business tool.

## Сигнатура
```text
create_return_request(
  order_id,
  item,
  reason,
  comment
)
```

## Аргументы
- `order_id` - обязательный номер заказа.
- `item` - обязательное название товара.
- `reason` - обязательная краткая причина.
- `comment` - краткое описание фактов.

## Возможные ответы
- `created` + `request_id`
- `invalid_order`
- `already_exists` + существующий `request_id`
- `missing_required_field`
- `tool_error`

## Проверки инструмента
1. Проверить обязательные поля.
2. Проверить существование заказа.
3. Проверить активный дубль.
4. Создать запись.
5. Присвоить `request_id`.
6. Вернуть результат.

## Что tool не решает
Tool не определяет:
- разрешен ли возврат по правилам;
- нужен ли человек;
- можно ли обещать компенсацию;
- надо ли вообще создавать заявку.

Это решение принимает Agent на основании контекста и базы знаний.

## Human confirmation
В базовом сценарии перед созданием заявки используется подтверждение человека.

## Reset
После учебной попытки состояние заявок возвращается к `return_requests_seed.csv`.


## Обработка дубля как учебный сценарий

Agent может не знать заранее, что по заказу уже существует активная заявка. Если пользователь явно просит зарегистрировать случай и других оснований для отказа нет, Agent после подтверждения может вызвать `create_return_request`.

Если tool возвращает `already_exists`, Agent:
1. не утверждает, что создал новую заявку;
2. сообщает о существующей заявке;
3. при нерешенном повторном обращении передает случай человеку.

Такой сценарий показывает границу между решением агента и бизнес-проверками внешнего инструмента.
